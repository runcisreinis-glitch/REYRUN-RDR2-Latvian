## 工作慢在哪里

**并发限制和截止时间。**10 月第十轮配置了 12 个本地工作配置，同时最多运行 3 个。预计分发 84 个小批次，实际发出 45 个。到期时有 39 批共 179 行未发出。一份返回结果带了错误 ID。校对开始时，固定下来的输入有 90 条本地草稿，最终共有 264 条通过结构检查，部分在校对开始后才返回。我们保存校对者实际读过的版本，拒收 ID 错误的文本；靠猜测补 ID 会掩盖问题。调整后，每个请求有独立期限，持久化队列继续分发后续任务。

**终审和写入。**11 月 2 日 22:04 时，3,286 条已校对文本在等导入，另有 18,393 条等终审。上一次导入于 08:55 完成，起草和校对一直持续到晚上。增加译者并不能把这些待导入文本写进游戏。11 月 6 日，Steam 更新完成，部署前检查也通过了，但上一次运行仍占用数据库写入权。预检查本身没有修改文件。恢复时应确认先前写入进程的状态，核对候选版本与备份，从首个未完成步骤继续。

**重复处理。**11 月 8 日审查了四名通过 API 工作的校对者此前 24 小时的记录。5,650 份报告含服务方的用量统计，合计 94,683,901 个 token。流程分两步编辑和复查已有草稿。此次审查没有算出账单金额或每条批准文本的用量。由于保存了原始回答，另外找不到的 2,093 条得以恢复。其他项目若校对积压，可先停发新请求，恢复保存的结果，再把剩余预算留给确实未解决的 ID。

## 译文错在哪里

本地草稿把 “You're right” 译为 “Tu esi taisnīgs”，意思是对方为人公正；同意对方观点时应说 “Tev taisnība”。另一处把 “maniac” 译成 “atraitis”（鳏夫）。这些错误能通过 JSON 和 XML 格式检查。因此校对时通读原文与译文，记录误解的词义，把带来源的改正示例交给下一批使用。

相同资源组有时能提供线索，但 ID 顺序不能证明谁在说话，也不能确定下一句。部分记录只有文本 ID，缺少可靠的说话者或场景信息。存疑条目单列，并附上给编辑的具体问题。对相同的 24 条原文，一次试验比较了包含全部示例的指令和只保留精选示例的短指令。两种结果都有严重的语义和语言错误，请求顺序和缓存使用也不同，不能据此判断整个项目会提速。

## 最后 7,049 条怎样写入游戏

先恢复以前已校对的 1,348 条。其余 5,701 条核对了 104 批中的最新编辑决定。377 条有意保留原拼写，包括按键名、品牌名和角色说的外语台词。如果把所有和原文相同的条目一律重译，就会重复已经完成的工作。

同一时刻由一个进程写入发布版。先检查候选文本，准备导入，在数据库副本上演练，再应用到正式数据库、生成 XML、核对目标安装目录并写入。随后重新打开游戏里的 XML，比较全部 ID 和文本。此前已写入的 246,024 条全部保留原有措辞。后来对新增内容中的 29 条作了修订，总数没有变化。

其他游戏也可按同一时间段分别统计初稿、终审批准项和在已安装文件中验证的新 ID，并记录耗时与可见原文字符数。已安装条目的修改、有意保留的原拼写和待解问题各列一栏，接手者便能判断下一步是翻译、做编辑决定，还是写入现成文件。
